## Mechanics addendum to paste after Prompt 1

The client-supplied breakdown is useful for identifying gameplay systems. It also mixes observed Zero Hour behavior, uncertain implementation claims, and suggested new architecture. These prompts tell Claude to keep those categories separate.

| Claim in the supplied description | How to use it |
| --- | --- |
| Three factions split into three Generals equals nine playable factions | Zero Hour has three base factions **and** nine specialist armies. Our new project has the nine *country/coalition sides requested by Mohammed*; optional commander doctrines can come later. |
| Dual resource framework | Specify one spendable credit balance plus power/capacity and other constraints. Cash may come from several sources; power is not a second currency. |
| China passively collects from supply docks | Supply Trucks physically shuttle to depots; Hackers are a separate secondary income method. USA Chinooks and GLA Workers are different active gatherers. |
| Persistent right-side command console | Mohammed's tested Zero Hour UI has a bottom command bar and lower-left minimap. Make the new layout original and scalable rather than treating a right sidebar as a required replica. |
| Particle Cannon is a General's Power | It is a constructed superweapon. Keep constructed superweapons, experience/rank purchases, and unit veterancy as distinct systems. |
| Hierarchical A* with group flow fields, mandatory ECS, snap grid and radius-limited base placement, or lockstep **or rollback** as a fixed requirement | Inspect the actual source and benchmark. Existing code has pathfinding cells, object templates and behavior modules, plus frame-numbered network command packets. Flow fields, a replacement ECS, snap placement, and rollback are **proposals**, not proven properties or mandatory upgrades. |
| Every oil well is unraidable, all bridges repairable, all props destructible | Treat these as map/object design options. Specify capture, damage, sight and pathfinding behavior per object and verify each in-engine. |

### Prompt 8 — economy, logistics and faction differentiation

```text
Implement the economy and faction systems for our original RTS, beginning with the two-faction vertical slice and leaving an extensible design for all nine sides: Iran, Iraq, North Korea, Taiwan, China, Japan, Europe coalition, Ukraine and USA. Model one spendable credit balance, finite contestable deposits, active gatherers that travel and can be intercepted, optional faction-specific secondary income, neutral capturable economic sites, builder construction, production costs/times and a power/capacity rule where relevant. Do not copy Zero Hour's unit names, values, interfaces or artwork. Treat the old game's Chinook/Worker/Supply Truck contrast as a reference for asymmetry, not a demand that our nine factions each get a clone of one.

The gameplay and balance agents must write an economy specification with units for every quantity and formulas for cargo value, trip time, delivery, depletion, income tick, investment payback, build time, power availability and cap, plus rounding rules and fixed-step behavior. Define when an income source can be raided, denied, rebuilt or recaptured. Document each faction's intended economic advantage and its counterplay; avoid a passive income strategy that makes map control irrelevant. The map agent must place deposits and neutral sites so mirrored starts have comparable travel time and expansion opportunities.

Implement a minimal real version in B2: both sides can gather, spend, lose gatherers, replace them, contest a neutral objective and recover from a depleted starting node. Verify credit conservation, power/build behavior, opening build orders, replacement time, income curve, snowball risk and a human-versus-AI match. Return a table of actual measured timings and balance issues. Expand the remaining seven sides only after the two-side economy is playable.
```

### Prompt 9 — combat, progression, terrain and interaction contracts

```text
Design and implement distinct but compatible combat systems: data-defined weapons/damage tags and armor classes; projectile travel and splash/area effects where supported; target priority, sight/fog, movement and pathfinding; unit counters; unit veterancy; a separate commander rank/ability tree; upgrades researched at buildings; and optional late-game constructed superweapons. Write explicit timing, range, cost, cooldown, damage and counter rules for each object, with data validation and no unexplained hardcoded balance constants. Make the first roster show infantry, vehicle and anti-vehicle/air counterplay without requiring every faction to use identical units.

The map and gameplay agents should specify occupancy and combat behavior for garrisons, capturable neutral structures, elevation, chokepoints and route alternatives. Bridges may be destructible/repairable only if the engine and a specific original map support reliable pathfinding updates. Destructible cover/props and hazard zones need visibility, lifetime, damage, cleanup and save/replay rules. The art/audio agents must give every selected unit, weapon impact, veterancy change and ability a readable in-game visual/audio cue, with original content provenance.

Deliver a combat matrix of attacker role versus armor/target role; a progression table showing how unit veterancy differs from commander powers; and small reproducible test scenarios for target acquisition, garrison entry/exit, cover destruction, sight on elevation, ability cooldown, damage over time and counterplay. Implement the B2 subset first. Mark every unimplemented feature as a future ticket, not a working menu button.
```

### Prompt 10 — modes, AI and competitive engineering

```text
Plan a complete RTS product without trying to finish every mode in the first build. For skirmish, support selectable maps, sides, teams, starting credits, difficulty, victory conditions and fair AI personalities (for example aggressive expansion, defense-first and air-focused). For a later original challenge ladder, design distinct scripted commander encounters and rules for unlocks/rewards. For campaigns, prepare original missions, briefings, triggers, secondary objectives and in-engine cinematics; do not copy Zero Hour's stories, generals, actors, news footage or exact mission sequence. Show which systems are reusable between skirmish, challenges and campaigns.

The AI agent should first deliver reliable deterministic macro and tactical behaviors that share the normal economy and actions available to players. Scripted boss modifiers must be disclosed by the mode. Optional local LLM advisers or directors belong to a later single-player experiment with bounded actions, latency handling and save/replay semantics; they are not a substitute for core combat AI.

For competitive multiplayer, inspect the existing frame-command networking, replay and CRC behavior. Preserve deterministic fixed-step state and validate identical content hashes and desync logs. Evaluate whether the current command synchronization can be improved; do not casually replace it with rollback or promise rollback support. Define authoritative match settings, lobbies, reconnect/leave handling, observers, replays, balance telemetry, map veto or pool rules, fair starting positions and anti-cheat boundaries for a later release. Build single-player B2 first, then use repeatable two-client tests as the network gate. Report evidence for each mode separately.
```
